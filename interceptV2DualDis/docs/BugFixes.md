## 2026-07-05 — `region_estimator` regressed to near-chance under `schedule="adaptive"`; two related runner bugs fixed

**What changed:** `goalkeeper_multidisc_amp_runner_cfg()`'s `"schedule"` changed from `"adaptive"` to `"fixed"` (`tasks/goalkeeper_multidisc_amp_cfg.py`). Also fixed in `him_amp_on_policy_runner.py`: `learn()` now sets `self.current_learning_iteration = it` right before each periodic checkpoint save (previously only updated once, after the whole `learn()` call returned, so every intermediate `model_{it}.pt`'s embedded `"iter"` field was always `0`); `load()` now restores `self.current_learning_iteration = loaded["iter"]` (previously never touched it at all, so any resume would silently restart iteration numbering at 0 and could overwrite/collide with existing checkpoint filenames in the same run directory).

A live diagnostic (loaded `model_500.pt` and `model_5250.pt`, drove 512 envs with the trained policy 400 steps, compared `region_estimator`'s live argmax against `env._region_id`) found: `model_500` — 38.5% accuracy (chance=25%), real signal on all 4 classes; `model_5250` — 27.7% accuracy, confusion matrix shows near-total collapse onto `left_near`/`right_near` only, **unable to distinguish true left from true right at all** (~48%/52% split regardless of true side), "far" classes almost never predicted (6% vs true 50%). Comparing against `Humanoid-Goalkeeper/rsl_rl/rsl_rl/algorithms/him_ppo.py` (this runner's origin): G1 defaults to `schedule="fixed"` and `g1_29_config.py` never overrides it — the proven reference run used a constant LR throughout. Confirmed empirically: `model_5750.pt`'s saved `optimizer_state_dict` shows `lr=7.59e-5` for every param group — 13x below the configured `1.0e-3`, sitting at the scheduler's floor. This also plausibly explains the double-step failure: the actor's own belief about which region it's in was unreliable, and by the time it mattered the whole network's effective learning rate had collapsed, leaving no room to learn a behavior (double-stepping on far balls) that depends on that signal.

The iteration-tracking bugs were fixed alongside because resuming training to test the schedule fix requires them: without the fix, a resume would restart `it` at 0 and silently overwrite `model_0.pt` onward in the same directory.

**Correct value:** `schedule="fixed"`, `learning_rate=1.0e-3` (unchanged base value, now never adaptively touched). Iteration counter now correctly tracked through save/load.

**Evidence:** Live probe confusion matrices (see above) and the checkpoint's own `optimizer_state_dict` lr values are the direct evidence for the collapse; the G1 default comparison is the basis for the fix. **Not yet independently confirmed as the fix** — training was resumed from `model_5750.pt` (fresh optimizer state, `load_optimizer=False`, to avoid inheriting Adam moments tuned for a near-zero LR regime) with `schedule="fixed"` to observe whether `Loss/est_region`/region accuracy recovers; results pending.

## 2026-07-06 — `reset_ball_rolling`'s y_end sampling ignored one-sided region ranges: ~50% wrong left/right, "far" regions landed near 75% of the time

**What changed:** `reset_ball_rolling` (`mdp/events.py`) now branches on whether `y_end_range` is one-sided (`y_end_range[0] * y_end_range[1] > 0`, i.e. doesn't straddle zero) vs the original two-sided/symmetric case. For one-sided ranges (all 4 region-conditioned calls from `reset_ball_rolling_by_region`), the sign is now taken directly from `y_end_range` (never randomized), and the sampled magnitude is lerped within that range's own `[lo, hi]` bounds (`lo=min(|bounds|)`, `hi=max(|bounds|)`; `inner=lo`, `outer=lo+(hi-lo)*d` at difficulty `d`) instead of the generic two-sided dead-zone constants. The original two-sided branch (used only by the single-disc task's plain `reset_ball`, `y_end_range=(-0.9,0.9)`) is unchanged.

**Why it was wrong:** `reset_ball_rolling` was written once for the generic, symmetric, either-side target (`(-0.9,0.9)`) and reused verbatim by `reset_ball_rolling_by_region` for the 4 per-region *one-sided* ranges (`left_near=(0.15,0.5)`, `left_far=(0.5,0.9)`, `right_near=(-0.5,-0.15)`, `right_far=(-0.9,-0.5)`) without adapting the sign/magnitude logic. Two independent defects stacked: (1) `side = torch.where(rand()>0.5, 1, -1)` always re-randomizes the sign with a 50/50 coin flip regardless of `y_end_range`'s actual sign — a "left_near" env's ball landed on the *right* side of the goal line roughly half the time, and vice versa for every region; (2) the magnitude bounds (`inner`/`outer`) were derived from the fixed generic constants `_Y_INNER=0.15`/`_Y_OUTER=0.35` and `max_half`, never clamped to the region's own `lo` bound — so a "far" region (`0.5`–`0.9`) sampled magnitudes as low as `0.1`, deep inside "near" territory, at every difficulty level once `d` was past the initial ramp.

This was caught while auditing whether interceptV2DualDis's region/ball-estimator mechanism matched `Humanoid-Goalkeeper`'s (per this project's standing rule to verify every mechanism against the G1 reference before trusting it) — G1's own 6-region split (`legged_robot.py:916-960`, `g1_29_config.py` `ranges_0`..`ranges_5`) uses **disjoint, non-overlapping height/width bounds per region with no re-randomized sign**, so this class of bug can't occur there; the SGK/interceptV2 region-conditioned ball spawn is a new mechanism without a direct G1 analogue, and its sign/magnitude logic was never checked against the region ranges it was actually being fed.

Verified empirically (20k-sample Monte Carlo of the exact pre-fix formula, at `d=1.0`, matching the checkpoint under test at the time — `model_3000.pt`, ball_difficulty curriculum saturated): `left_near` sampled negative (wrong side) 49.4% of the time and landed inside its own intended `[0.15,0.5]` band only 44.4% of the time; `left_far` sampled negative 49.8% of the time and landed inside its own intended `[0.5,0.9]` band only **25.1%** of the time (i.e. 75% of "far"-labeled balls were secretly easier near-magnitude shots). `right_near`/`right_far` showed the mirror pattern. This directly explains two previously-unresolved symptoms: the region_estimator's persistent, unresolved left/right confusion in the live probe (34.9% accuracy at `model_3000`, weak-to-nonexistent left/right separation despite the region_estimator LR-collapse fix already applied and holding) — because the ground-truth label (`env._region_id`) was statistically decorrelated from the ball's actual observable side for ~50% of samples — and the user-reported failure of far-side shots to converge on the double/triple-step AMP reference motions, since 75% of nominally-"far" episodes never actually presented a far shot for the policy to practice on.

**Correct value:** one-sided ranges now sample sign-locked, magnitude-lerped-within-own-bounds `y_end`; see fix description above. Verified via direct Monte Carlo of the post-fix formula: all 4 regions land inside their own intended range 100% of the time, at every difficulty level from `d=0` (deterministic at the region's inner edge) to `d=1` (full region span).

**Evidence:** Reproduction and fix verification scripts run standalone (not committed as tests — see gap noted below). Existing `tests/simple_goalkeeper/test_regions.py` did not catch this because it monkeypatches `reset_ball_rolling` entirely and only asserts on the `y_end_range` *parameter* passed to it, never exercising the actual sampling math inside — a real test-coverage gap; a follow-up should add a test that calls `reset_ball_rolling` (or an isolated helper) with a one-sided range and asserts the sign/bounds directly. Not yet confirmed against a full training run — this fix requires a fresh run (the in-flight `2026-07-06_15-13-34_region_fix_g1_match_2026-07-06` run's region_estimator and actor were trained against the corrupted ball-spawn distribution from iteration 0, so resuming it would carry the poisoned region conditioning forward; restarted fresh instead).

## 2026-07-07 — `reset_ball_rolling`'s `env._rsi_cross_y` used the wrong crossing-fraction formula (cos(angle) instead of the X-ratio)

**What changed:** the goal-line crossing-Y formula in `reset_ball_rolling` (`mdp/events.py`) changed from `y_start + (y_end - y_start) * (x_start + 0.3) / horiz_dist` to `y_start + (y_end - y_start) * (x_start / (x_start + 0.3))`.

**Why it was wrong:** the ball travels in a straight line from `(x_start, y_start)` to the aim point `(-0.3, y_end)` — 0.3 m *behind* the actual goal line. Parametrizing the line by `f ∈ [0,1]` (0 at spawn, 1 at the aim point), `X(f) = x_start - f*(x_start+0.3)`. The goal line is at `X=0`, not at the aim point, so the correct crossing fraction is `f = x_start / (x_start+0.3)`. The old formula instead computed `f = (x_start+0.3) / horiz_dist` where `horiz_dist = sqrt((x_start+0.3)² + (y_end-y_start)²)` — that's `cos(trajectory angle)`, a completely different quantity that happens to also land in `(0,1]` but has no geometric relationship to "how far along the path is the goal line." The two formulas disagree on every diagonal shot (e.g. `x_start=2.0, dy=0.5`: correct `f=0.870` vs buggy `f=0.977`), making the buggy version place `cross_y` closer to `y_end` than the true crossing point.

Found while investigating a user report that interceptV2DualDis's play viewer showed "near" balls incorrectly getting the blue/green two-stage split — traced the same bug independently to `SimpleGoalKeeper`'s `reset_ball_rolling` (see its `docs/BugFixes.md`, same date), which turned out to have the correct formula computed first and then a *second*, leftover duplicate block silently overwriting it with this exact wrong formula — almost certainly the source this project's single (buggy, never-corrected) copy was ported from. Proved mathematically that this bug is bounded and could not be the actual cause of the reported symptom: since `f ∈ (0,1]` for both formulas, `cross_y` can never leave the interval `[min(y_start,y_end), max(y_start,y_end)]` — a legitimately-narrow target (`|y_end| ≤ 0.5`, with `|y_start| ≤ 0.3`) can never produce a computed `cross_y` exceeding `0.5` regardless of which formula is used. Confirmed via two direct empirical tests (region-conditioned `play=True`/`play=False` configs, and a fresh 95-episode wide-flag consistency check on the sibling SGK project): `env._blue_wide`/the two-stage gate correctly separates near from far in every sampled episode, before and after this fix. The actual explanation for the reported symptom is a design fact, not a bug: "wide" is a purely *lateral* threshold (`|crossing_y - start_y| > 0.5`), independent of forward spawn distance — a physically close-spawning ball can legitimately have a large lateral target and correctly trigger the two-stage split.

**Correct value:** `env._rsi_cross_y[env_ids] = y_start + (y_end - y_start) * (x_start / (x_start + 0.3))`.

**Evidence:** 48/48 existing tests pass unchanged (no test asserted the exact numeric value of `_rsi_cross_y`, only the downstream `wide`/region classification, which this fix cannot affect — see bounded-impact argument above). This is a real accuracy fix for the footreach/foot_proximity/stopball/softstop target geometry on every diagonal shot, not a classification fix — did not warrant restarting the in-flight `blue_ball_gate_2026-07-06` run (its impact is bounded within the existing near/far envelope, unlike the section-12 sign/magnitude bug which flipped classifications outright).

## 2026-07-07 — region-far episodes only triggered the two-stage `wide` gate ~80-83% of the time, not 100%: crossing-point/aim-point mismatch

**What changed:** `_get_reach_target_y` (`mdp/rewards.py`) now ORs the threshold-based `wide` flag with the region's own far/near ground truth when `env._region_id` is set (region-conditioned task only): `wide = wide | _REGION_IS_FAR.to(env.device)[region_id]`, where `_REGION_IS_FAR` is a small module-level lookup built from `regions.REGION_NAMES` (`name.endswith("_far")`). But `regions.py`'s `_REGION_Y_END_RANGE` (the region near/far boundary, also `0.5`) is defined on `y_end` — the ball's *aim point*, 0.3 m **behind** the goal line, per `reset_ball_rolling`'s own trajectory design. Per the crossing-fraction fix directly above, `_rsi_cross_y = y_start + (y_end-y_start) * f` with `f = x_start/(x_start+0.3) < 1` always — so the crossing point is systematically smaller in magnitude than `y_end` whenever `y_start`/`y_end` share sign (which every region-conditioned range does by construction). This means a region-far episode whose `y_end` sits near the region's own `0.5` inner edge computes a crossing point *below* `0.5` and gets misclassified as narrow — even though the ball was deliberately spawned as a "far" shot by the region system. **Correct value:** region ground truth (`env._region_id`) is authoritative over the threshold-derived value for the region-conditioned task; see fix above. Verified empirically: `left_far`/`right_far` now trigger `wide=True` 100.0%/100.0% (up from 80.4%/83.3%), `left_near`/`right_near` unchanged at 0.0%/0.0%.

**Evidence:** 48/48 tests pass. Empirical before/after measurement (64 envs, forced `difficulty=1.0`, 60 steps): before — `left_near` 0/48, `left_far` 37/46 (80.4%), `right_near` 0/48, `right_far` 40/48 (83.3%); after — `left_near` 0/48, `left_far` 43/43 (100%), `right_near` 0/48, `right_far` 48/48 (100%). **Training restarted** (not resumed — this changes which episodes require the landing gate, a large enough behavior change for the exact mechanism this run exists to test that continuing to train under the old, partially-leaky gate would contaminate the results) per the user's standing instruction to restart on finding something that needs fixing; see HANDOFF.md for the new run's launch details.

## 2026-07-07 — `blue_ball_landed` fired from a foot sweeping past the blue midpoint mid-stride, not landing there: `landing_radius` tightened 0.05 -> 0.02

**What changed:** `_get_reach_target_y`'s `landing_radius` default (`mdp/rewards.py`) tightened from `0.05` to `0.02`.

**Why it was wrong:** user reported watching `sgk_play` and seeing the assigned foot's actual ground contact land near the GREEN target while `blue_ball_landed` had already fired — the policy was still doing one continuous big step/leap, not a genuine paced double-step, despite the landing gate supposedly requiring a stop at the blue midpoint first. Blue and green share the same X (the goal line) and are always `>= wide_threshold/2` apart in Y for a wide crossing, so a foot planting AT green cannot itself be within `0.05` m of blue — ruled that out directly. The actual mechanism: blue sits directly on the straight-line path from the robot's stance to green (same X, Y strictly between the two), so a single continuous stride/leap toward green necessarily sweeps *through* blue's Y-coordinate at some point mid-flight. If the `feet_contact` sensor registers a momentary/glancing contact during that pass-through (sensor noise, a low ground-clearance shuffle, foot-scuff during swing phase) while the foot's horizontal position happens to be within `landing_radius` of blue, `newly_landed` latches — even though the policy never intended to stop there and continues on to plant at green. This is the same category of exploit SGK found and fixed for the identical reason on 2026-07-05 (`landing_radius` `0.3` -> `0.05`, "a single ordinary stride toward the true (green) target passes close enough to the blue midpoint, mid-stride, to satisfy the old landed check without the robot ever stopping there") — this project inherited SGK's already-tightened `0.05` at port time, but that apparently still wasn't tight enough here.

**Correct value:** `landing_radius=0.02`. Shrinking the radius doesn't eliminate the underlying exploit in principle (a sweep could in theory still graze an arbitrarily small radius by chance), but makes accidental pass-through contact far less likely, requiring something much closer to a genuine, deliberate plant at the exact midpoint coordinate.

**Evidence:** 48/48 tests pass (no test asserted the exact numeric threshold, only qualitative landed/not-landed behavior at a coarser radius, unaffected by the tightening). Not yet independently validated against a training run — behavioral confirmation requires watching a checkpoint from a run trained under this tighter radius. **Known limitation, not fully resolved:** this is a magnitude reduction, not a structural fix — a sufficiently athletic/fast single stride could still theoretically satisfy an arbitrarily small radius by chance. If the one-big-step behavior persists even at `0.02`, the next step should be a velocity-based check (e.g. require the assigned foot's horizontal speed to be near zero at the moment of contact) to distinguish a genuine plant from a foot merely passing through at speed — flagged for a follow-up if this radius alone doesn't resolve it. **Known caveat, carried over from the 2026-07-07 viewer-fix entry above:** `env._blue_airborne_at_reset` is a per-episode latch that can be true even when the *specific* later landing event wasn't actually free — this project's 80% `continue_keep` RSI branch means donor poses are mid-motion by construction, so some foot is almost always airborne within an episode's first 2 steps regardless of whether the eventual blue landing was earned. This means the tightened gate may over-reject some genuine mid-episode landings whose episode merely happened to start with an early airborne transition unrelated to the actual landing. Accepted as the best available proxy — it's the same definition already used for the `blue_landed_genuine`/`blue_landed_rsi_assisted` metrics, so gate and diagnostics stay consistent; revisit if training shows the gate essentially never opens even as the policy visibly improves.

**Evidence:** 48/48 tests pass (no test asserted the old permissive gate value). ## 2026-07-07 — blue-midpoint landing check was position-only, so nothing distinguished a genuine plant from a fast sweep-through; also nothing disincentivized sweeping: `landing_speed_threshold` added, `landing_radius` loosened 0.02 -> 0.08

**What changed:** `_get_reach_target_y` (`mdp/rewards.py`) now also requires the assigned foot's horizontal speed (`torch.norm(assigned_foot_vel[:, :2], dim=-1)`, from `robot.data.body_link_lin_vel_w`) to be below a new `landing_speed_threshold=0.5` m/s at the moment of contact, in addition to the existing position check. `landing_radius` loosened back from `0.02` to `0.08` now that the speed gate — not radius — is responsible for ruling out grazes.

**Evidence:** 48/48 tests pass. ## 2026-07-08 — added `blue_overshoot_penalty`: no cost to ignoring the blue waypoint entirely meant PPO had no gradient pushing it away from that local optimum

**What changed:** new reward term `blue_overshoot_penalty` (`mdp/rewards.py`), weight `-30.0` (`tasks/goalkeeper_env_cfg.py`). Penalizes the assigned foot for advancing past the blue midpoint (toward green) on a wide crossing before genuinely landing there (`env._blue_wide & ~env._blue_landed`), scaled by how far past (`clamp(signed_progress - landing_radius, 0, 0.5)`, deadband matches the existing `landing_radius=0.08` arrival radius). Zero on narrow crossings and once genuinely landed.

**Why it was wrong (or rather: incomplete) before:** the 2026-07-07 landing-rate diagnostic (see the two entries above) established that even under the tightened, airtight gate, the policy still wasn't discovering the genuine two-stage plant — it was sweeping straight past blue with zero reward for doing so. On investigation (prompted by the user asking for a full audit and floating "a negative reward for going past blue without landing" as one option): a wide episode where the policy ignores the blue waypoint entirely earns exactly the same reward (zero, from `stopball`/`softstop`/`blue_ball_landed`, all landing-gated) as one where it genuinely tries and fails. With no cost differential between "didn't try" and "tried and missed," PPO has no gradient distinguishing them — and since narrow crossings (~half the region-sampled distribution) already pay out fully with minimal movement (a near-default stance blocks many center-ish shots), "specialize in narrow, ignore wide entirely" is a stable local optimum with no force pulling the policy out of it. This is a distinct root cause from the two entries above (which fixed how *achievable* a genuine landing is) — this fixes the complete *absence of exploration pressure* toward attempting one at all.

**Why `footreach`'s `vel_sigma` was NOT touched (user caught an overcorrection in the original plan):** the initial idea (this session's prior message) proposed neutralizing `vel_sigma` during the blue-approach phase, reasoning that it rewards speed toward the target and so works against stopping. Rereading `footreach()` (`rewards.py`) shows this diagnosis was imprecise: `vel_sigma`'s direction is computed from `lateral_error = reach_target_y - robot_y_w`, and `reach_target_y` (from `_get_reach_target_y`) already flips from blue to green exactly on `env._blue_landed` — so `vel_sigma` already only rewards velocity toward blue pre-landing, never toward green early. The actual gap wasn't *what* it targets, it's that nothing penalizes carrying that speed past the target without stopping. Left `vel_sigma` untouched; `blue_overshoot_penalty` supplies the missing piece instead. The combination (fast approach still rewarded + overshoot penalized) should shape an accelerate-then-decelerate-to-a-plant profile matching what's actually in the `LeftDoubleStep`/`RightDoubleStep` AMP demo clips (see the "do i need a better dataset" investigation, same day: the demo's own foot trajectory shows exactly this shape, decelerating to near-zero velocity at a dwell point almost exactly at the geometric midpoint of its total displacement) — rather than needing a separate hand-authored deceleration reward.

**Weight `-30.0`:** not empirically tuned, chosen to be comparable in magnitude to the largest per-step positive rewards (`footreach` max ~10, `foot_proximity` max ~5) so it's a meaningful counter-pressure without being an extreme hard-constraint-scale penalty (cf. `penalize_kneeheight`/`penalize_sharpcontact` at -100). Flagged as the first thing to revisit if training shows either no effect (too weak) or destabilization (too strong).

**Known interaction, not yet resolved:** the velocity-gated landing check added in the entry above still checks foot speed at the instant of the contact-transition, which the same-day diagnostic showed rejects genuine plants (0% genuine, up from 1.4% pre-velocity-gate) because a real footstrike still carries residual velocity at first contact. This penalty doesn't fix that timing bug — it only adds pressure to *attempt* stopping at blue, which should produce more attempts at genuine plants, but whether those attempts can actually register as `_blue_landed` still depends on the separately-flagged, unfixed velocity-check-timing issue. Left as-is per user judgment ("i dont think this is really a big problem") when this was surfaced; worth revisiting together if this fix alone doesn't move the genuine-landing rate.

**Evidence:** 48/48 tests pass. Live smoke test (8 envs, zero-action policy, 60 steps) confirmed the term registers and runs without error. Not yet validated for actual learning outcome. Training restarted (not resumed) — new reward term changes the return landscape enough that continuing under the old one would conflate results.

## 2026-07-08 — AMP setup brought to literal parity with G1: gradient penalty, discriminator width, and replay buffer

**What changed (`src/simple_goalkeeper/rsl_rl_multi/multi_disc_amp_ppo.py`, `tasks/goalkeeper_multidisc_amp_cfg.py`, `beyondAMP/source/rsl_rl_amp/rsl_rl_amp/storage/replay_buffer.py`):**

1. **Gradient penalty:** `discr.compute_grad_pen(..., lambda_=10)` (no further scaling) → `discr.compute_grad_pen(..., lambda_=5) * 0.1`. Effective coefficient 10 → 0.5.
2. **AMP discriminator loss weighting:** `amp_loss = amp_loss + 0.5*expert_loss + 0.5*policy_loss` → `amp_loss = amp_loss + expert_loss + policy_loss` (full sum, not average).
3. **Discriminator trunk width:** `amp_discr_hidden_dims: [256, 256]` → `[512, 256]`.
4. **AMP "policy" sample source:** `amp_storages` (per-region `ReplayBuffer`, previously a persistent 250k-transition FIFO queue sampled across many updates) now cleared (`rb.clear()`, new method added to `ReplayBuffer`) at the end of every `update()`, alongside the existing `self.storage.clear()`.

**Why:** user explicitly requested literal parity with G1's AMP mechanism ("i want the same amp setup as g1 not the same outcome... same code... no unnecessary divergence"), not just equivalent functionality. Dispatched a research agent to do a line-by-line comparison against `Humanoid-Goalkeeper/rsl_rl/rsl_rl/algorithms/him_ppo.py` and `rsl_rl/rsl_rl/modules/amp.py`. Findings, each independently confirmed by direct code reading:

1. G1's `compute_grad_pen` (`amp.py:124-152`) defaults to `lambda_=5`; `compute_loss` (`amp.py:169`) applies an additional `* 0.1` on top: `grad_pen = self.compute_grad_pen(expert_obs, agent_obs) * 0.1`. Net effective coefficient `0.5`. This port used `lambda_=10` with no further scaling — effective `10`, ~20x stronger discriminator regularization than G1, which over-flattens the discriminator's logit landscape (a discriminator regularized this hard toward a near-constant output is a blunter, less spatially-informative reward signal).
2. G1's `gail_loss = expert_loss + policy_loss` (`amp.py:168`, unweighted sum). This port averaged instead (`0.5 * expert_loss + 0.5 * policy_loss`), halving `amp_loss`'s relative magnitude against the rest of the total loss for no documented reason.
3. G1 never overrides `AMP.__init__`'s `hidden_dims` kwarg (`him_on_policy_runner.py:85` constructs `AMP(num_obs, amp_coef, device=...)` with no `hidden_dims` arg), so it uses the class default `[512, 256]` (`amp.py:87`). This port used `[256, 256]` — half the trunk capacity, an undocumented divergence, not a deliberate one.
4. G1's discriminator has **no persistent replay buffer at all**. Its "policy" sample for the discriminator loss (`amp_obs_batch` in `him_ppo.py:181-182`) is unpacked directly from the same `HIMRolloutStorage` minibatch generator as every other PPO quantity — i.e. strictly the current on-policy rollout, and `self.storage.clear()` wipes it every `update()` (`him_ppo.py:324`). This port's `amp_storages` were a 250,000-transition FIFO `ReplayBuffer` per region, populated every env step and never cleared, so the discriminator was trained against a stale mix of past-policy behavior spanning many prior updates instead of strictly what the current policy is doing. Since `ReplayBuffer` had no `clear()` method at all, one was added.

**What was checked and found to NOT be a divergence** (so left unchanged): the reward blend formula itself. G1: `rewards = amp_reward*amp_coef + raw_rewards*(1-amp_coef)`, `amp_coef=0.4`, `amp_reward = predict_reward(...)*0.5` (`him_on_policy_runner.py:175-185`, `amp.py:185-206`). This port: `reward = (1-lerp)*amp_reward + lerp*task_reward`, `lerp=0.6`, `amp_reward = amp_reward_coef * clamp(1-0.25*(d-1)^2, 0)`, `amp_reward_coef=0.5` (`amp_discriminator.py:64-72`). These are the same formula under different parameter names (`lerp=0.6` on task ≡ `amp_coef=0.4` on AMP — complementary), confirmed mathematically equivalent, not a rewrite. Also checked: `amp_min_normalized_std` (despite the misleading name, this is the actor's action-noise std floor, not an AMP/discriminator parameter at all — `him_amp_on_policy_runner.py`/`multi_disc_amp_ppo.py`) has no G1 equivalent because it isn't part of G1's AMP mechanism; left unchanged as an intentional, unrelated, already-existing addition. And: neither discriminator's observation space includes anything beyond `joint_pos`/`joint_vel` — both are strictly joint-space, so "AMP reward is blind to world/ball position" is true in both implementations, not a port-specific gap.

**Evidence:** 48/48 tests pass. Live end-to-end smoke test — 3 full training iterations (rollout collection + `update()`, 64 envs) via the actual runner — completed without error; confirmed `amp_storages[name].num_samples == 0` and `.step == 0` for all 4 regions immediately after the final `update()`, verifying the clear-every-update behavior actually takes effect at runtime, not just in isolation. Not yet validated for training outcome (whether a less-over-regularized, wider, strictly-on-policy discriminator changes AMP reward quality enough to matter for the still-open two-stage-stepping problem) — that requires watching this run's checkpoints.

## 2026-07-08 — blue-midpoint landing check was an instantaneous velocity check at the wrong moment: settle-window added

**AMP ruled out as the cause:** the escalation protocol's first branch is to re-audit AMP if the discriminator signal looks suspect. `Train/mean_discri_logits` showed values around -115 to -120, which looked alarming in isolation (a healthy discriminator logit for ±1 training targets should be roughly single-digit). Checked the actual logging code (`him_amp_on_policy_runner.py:238-239`) before concluding anything: `cur_discri_sum += d_logits` accumulates the raw logit **every step for the whole episode**, only flushed to the logged buffer at episode end — this is a per-episode sum, not a per-step or per-sample value. Dividing by a typical episode length gives a per-step logit around -0.5 to -0.8, unremarkable and consistent with ordinary (not collapsed) discriminator behavior. `Loss/AMP`/`Loss/AMP_grad` stayed small and stable the whole run; `mean_action_acc` stayed flat around 1.15 (no divergence). Conclusion: AMP is not the bottleneck this time — the blue-ball reward mechanism itself is.

**Diagnosis:** the settle-window landing check (previous entry) requires the assigned foot to be simultaneously in contact, within `landing_radius`, and below `landing_speed_threshold`, sustained for 3 consecutive steps. The only payoff for actually achieving "close and slow" was the sparse, conjunctive settle-window event itself. A policy has to stumble into that exact combination before any gradient reinforces it — and evidently hadn't in 5500+ iterations.

**Fix applied:** new dense reward term `blue_stick_landing` (`mdp/rewards.py`, weight `8.0`, `tasks/goalkeeper_env_cfg.py`) — `exp(-15·dist_to_blue) · exp(-3·foot_speed)` for the assigned foot on a wide, unlanded crossing, peaking exactly at "close AND stopped." Mirrors this project's own existing `cleanstop` pattern (rewards low ball speed near a target after a save) — same "reward stillness near a point" shape, applied to the foot approaching blue instead of the ball after a save. Gives ordinary gradient ascent an incremental path to the target condition (get closer → more reward; get slower while close → more reward) instead of requiring the exact conjunction to be found blind.

**Evidence:** 48/48 tests pass. Live end-to-end smoke test (3 full training iterations, 64 envs) confirmed the term registers (weight 8.0 visible in the active reward table) and runs without error. Not yet validated for actual learning outcome — this is exactly what the restart is for. `dist_sigma=15`/`speed_sigma=3` are not tuned against real footstrike dynamics; flagged for revisit if this doesn't move the genuine-landing rate at the next scheduled check.

## 2026-07-08 — scheduled 6500-iteration escalation: AMP discriminator init/reward-smoothing divergences found and fixed; landing_speed_threshold loosened; genuine landings still 0.0% across the whole run

**Context:** user raised the escalation threshold from 5000 to 6500 (curriculum `cu` hadn't reached 3 yet at 5000; `cu = int(mean_episode_length / 47)`, needs `mean_episode_length >= 141`). Also explicitly requested a mandatory re-comparison of the AMP architecture against G1 at this checkpoint: "amp reward seems to be really low." The bihourly cron ran both parts at iteration 8102.

**Part A — AMP magnitude re-audit (independent subagent, verify-from-scratch):** found and confirmed two real divergences, both now fixed in `beyondAMP/source/rsl_rl_amp/rsl_rl_amp/modules/amp_discriminator.py`:

1. **Missing explicit weight init.** G1's `AMP.__init__` (`amp.py:100-118`) leaves the first trunk layer at PyTorch default init but explicitly initializes every subsequent hidden layer *and* the final `amp_linear` output layer with `uniform_(-1, 1)` weights and zero bias (`DISC_LOGIT_INIT_SCALE = 1.0`). This port's `AMPDiscriminator.__init__` had no explicit init calls anywhere — all layers, including `amp_linear` (the layer that directly produces the discriminator logit `d`), used PyTorch's default `kaiming_uniform_`. For a `Linear(256, 1)` layer, PyTorch's default weight bound is `1/sqrt(256) ≈ 0.0625` — **~16x smaller** than G1's `uniform(-1,1)`. Fixed: added the same conditional init pattern G1 uses (first trunk layer default, every subsequent trunk layer + `amp_linear` explicit `uniform_(-1,1)`/`zeros_`).
2. **Missing reward-noise-smoothing.** G1's actual reward-time method, `predict_reward` (`amp.py:185-206`), perturbs the (normalized) input with `num_samples=20` Gaussian noise draws (`sigma=0.3`) and takes the **minimum** squared-error-from-1 over those samples before computing `clamp(1-0.25*err, 0)` — not a raw single-sample read. Min-over-samples systematically raises the computed reward relative to a raw single-point evaluation for the same underlying discriminator (it's effectively "best nearby match," a noise-robustness/smoothing technique). The port's `predict_amp_reward` used the raw single-sample `d` with no smoothing at all. Fixed: ported the identical noise-perturbation-then-min mechanism into `predict_amp_reward`; `d`/`d_logits` (used only for `Train/mean_discri_logits` logging) stays the raw unperturbed sample for interpretability, unaffected by this change.

Both were independently re-verified (not just trusted from the first pass) — the agent read both files fresh, computed the exact magnitude gap, and confirmed the port's discriminator structure is otherwise identical to G1's (hidden dims `[512,256]` match, `amp_normalizer` is a byte-identical `RunningMeanStd` port, same ReLU activation, no batch/layer norm in either). Verdict: "PARTIALLY CONFIRMED" as the dominant cause of low AMP reward specifically (real, verified divergences, but magnitude couldn't be attributed as *the* single cause without a live measurement) — both are now fixed regardless, consistent with the standing no-unnecessary-divergence policy.

**Part B — stuck/progressing judgment:** genuine blue landings measured 0.0% at iteration 8000 (0/1181 wide episodes) — the fifth measurement this run, with only one single 0.1% fluke (iteration 2500) among five checks. `blue_stick_landing`'s dense reward has stayed consistently nonzero (~0.06-0.12/episode) the whole run, meaning the policy demonstrably gets closer-and-slower over time without ever crossing the discrete settle-window threshold to register as a landing. Separately: curriculum crossed into `cu=3` right at this checkpoint (`softstop_curriculum` weight jumped 210→262.5, activating `correct_foot_save_curriculum` bonuses for the first time), and `mean_episode_length` regressed sharply at the same point (119.4→92.5) with `shank_height` terminations spiking (10.6→30.0) — a curriculum-transition destabilization, not necessarily a separate root cause, but a confound worth tracking.

**Judgment: stuck.** Five consecutive measurements at ~0% genuine, despite the settle-window fix, full AMP parity (round 1), and dense `blue_stick_landing` shaping all already being in effect, is a strong enough signal on its own.

**Fix applied (blue-ball side):** `landing_speed_threshold` loosened `0.5 -> 0.8` m/s (`mdp/rewards.py`, `_get_reach_target_y`). Rationale: `blue_stick_landing`'s consistent nonzero reward shows the dense gradient IS pulling the policy toward "close and slow" — but the discrete landing check never fires, suggesting the threshold itself may simply be stricter than a real, deliberate footstrike's residual velocity even while decelerating. Not yet independently confirmed against real footstrike dynamics; flagged for revisit.

**Evidence:** 48/48 tests pass. Live end-to-end smoke test (3 full training iterations, 64 envs): confirmed `amp_linear` weights now span up to ±1.0 with std ≈0.55-0.58 (matching a uniform(-1,1) distribution's theoretical std of 1/√3≈0.577 — the init fix is working as intended), training completes without error, and the 20x noise-sampling in `predict_amp_reward` adds no meaningful runtime cost (3 iterations in ~9.6s, comparable to pre-change).

**Training restarted** (not resumed) — pushed `model_8000.pt` (last checkpoint of the stuck run) before killing it. Three stacked changes in this restart (AMP init, AMP reward smoothing, landing_speed_threshold) — if the next check shows movement, a future investigation may need to isolate which one mattered, but bundling them was judged reasonable here since all three were independently well-evidenced fixes rather than speculative tweaks.

**Observed transient at restart (not a bug, documented for future monitoring):** the new run's `Loss/AMP`/`Loss/AMP_grad` spiked to 1299/1998 on iteration 0 (vs. the ~0.1-0.3 typical of the pre-fix runs), then decayed monotonically — 465→178→82→62→...→17 by iteration 19 for `Loss/AMP`, similarly for `Loss/AMP_grad`. `mean_action_acc` stayed in [1.56, 1.88] throughout, trending down, never approaching divergence. ## 2026-07-08 — ROOT CAUSE FOUND: `env._blue_airborne_at_reset` is a sticky per-episode latch that flagged 100% of landings as "free" regardless of when they actually happened, silently blocking `stopball`/`softstop` from ever firing on any wide episode all day

**Context:** user watched `sgk_play` on `model_2250.pt` and reported the robot still appeared to ignore blue and go straight for the ball. Asked for (1) a footreach correctness check, (2) a codebase-wide audit if footreach wasn't the problem, and (3) another independent AMP-vs-G1 architecture comparison, since "the amp has worsen i think looking at reward."

**Footreach: confirmed correct, both by code review and empirically.** Re-read `footreach`/`foot_proximity`'s target-switching logic — `reach_target_y` stays locked to blue's `half_y` for the entire approach on wide-unlanded episodes (`ball_close` structurally cannot become true until landed, since `~env._blue_wide` is false and `env._blue_landed` is false throughout). A live diagnostic driving the actual policy confirmed this empirically, not just by inspection: across 468-499 wide episodes, the assigned foot got within `landing_radius` **while in ground contact** in 97.6% of episodes. Footreach was never the bug.

**AMP: third independent audit came back clean.** A fresh, unbiased subagent re-compared `amp_discriminator.py` against G1's `amp.py` in full, plus `multi_disc_amp_ppo.py`'s `update()` against `him_ppo.py`'s, plus the normalizer and region-routing data volume. Confirmed-no-divergence on every major point already fixed in the two prior rounds; found one minor, likely-low-significance normalizer-width nuance (G1 tracks per-temporal-slot stats on the pre-concatenated state+next_state pair, the port shares single-frame stats across both slots) — not fixed, flagged as low-priority. This ruled AMP out as the remaining problem.

**The actual bug — found via a chain of live diagnostics, including catching a bug in my own diagnostic script along the way:**

1. Measured foot speed at the moment of closest in-contact approach to blue: median 0.815 m/s, just above the then-current `landing_speed_threshold=0.8`. Loosened to `1.0` (98.6% of near-contact moments were below 1.0). Re-checked against the *same* checkpoint — still 0.0% genuine. The threshold wasn't the blocker.
2. Hypothesized the settle-window's 3-consecutive-step requirement was never being satisfied. Wrote a diagnostic tracking `env._blue_settle_count`'s max value per episode — it showed 0% of episodes ever reaching count ≥ 2. Set `_BLUE_SETTLE_STEPS=1` to match. Re-checked — still 0.0% genuine, and the overall "landed at all" rate was *identical* to before the change (94.9-95.0% both times), which shouldn't happen if the settle requirement were actually the bottleneck.
3. That identical-before-and-after result was the tell: re-read my own settle-count diagnostic and found it filtered on `active = wide & ~landed`, which excludes the exact step a landing fires on (since `landed` flips true that same step) — so it could never observe the settle-count value that actually triggered a landing. The "never reaches 2" finding was a measurement artifact of my own script, not reality. **Reverted `_BLUE_SETTLE_STEPS` back to 3.**
4. With the real mechanism cleared of suspicion, investigated why "landed at all" was ~95% but "genuine" was always exactly 0%, by measuring **when** landings actually fire: `episode_length_buf` at the moment `newly_landed` transitions true, over 522 sampled landings. **Landings never fired before episode step 28 (median 35, max 86)** — clearly the product of 0.5+ seconds of real approach behavior, not free RSI credit. Yet **100% of these were still flagged `env._blue_airborne_at_reset=True`**.

**Root cause:** `env._blue_airborne_at_reset` (`rewards.py`, set inside `_get_reach_target_y`) is `env._blue_airborne_at_reset |= first_time_airborne & near_reset` — a sticky **latch** that goes true the first time the assigned foot is airborne within the first 2 steps of an episode, and **never resets** for the rest of a potentially 150-step episode. Since RSI donor poses are mid-motion by construction (documented repeatedly this project), some foot is airborne within the first 2 steps of nearly every episode, regardless of what happens afterward. The flag was never designed to answer "was *this* landing free" — only "was some foot briefly airborne near reset," which is true almost unconditionally and provides zero information about a landing occurring 30-85 steps later. Since `stopball`/`softstop`'s `landing_ok` gated on `env._blue_landed & ~env._blue_airborne_at_reset`, and the second term was essentially always false, **this silently made `stopball`/`softstop` unreachable on every wide-crossing episode for the entire duration of this investigation** — regardless of how well the policy actually performed. Every "genuine landing rate" measurement taken today (and likely going back to whenever this gate was first added, 2026-07-07) was reading this broken signal, not actual policy quality.

**Fix applied:** replaced the sticky latch with `env._blue_landed_was_free`, computed once per landing *event* rather than once per episode: `torch.where(newly_landed, env.episode_length_buf < _BLUE_LANDING_FREE_STEP_THRESHOLD, env._blue_landed_was_free)`, with `_BLUE_LANDING_FREE_STEP_THRESHOLD=10`. This asks the right question — was *this specific* landing achieved suspiciously early — instead of a stale historical flag. `env._blue_airborne_at_reset` is left in place (still computed, unused for gating) in case another diagnostic wants it. Updated `stopball`, `softstop` (`rewards.py`), and `metrics.blue_landed_genuine`/`blue_landed_rsi_assisted` (`metrics.py`) to use the new signal. Updated the scratchpad diagnostic script (`blue_landing_rate.py`) to match.

**Validation — re-ran the exact same diagnostic against the exact same checkpoint (`model_2250.pt`), changing nothing but the classification fix:**

| | Old (broken) classification | New (fixed) classification |
|---|---|---|
| Landed on blue (any) | 94.7% | 94.7% (unchanged, as expected — the landing mechanism itself was never broken) |
| Genuine | **0.0%** | **94.7%** |
| "RSI-assisted" / free | 94.7% | 0.0% |

The landing mechanism (footreach targeting, settle-window, speed threshold, position radius) has been working correctly this entire time. The training run has genuinely been learning to land on blue. The problem was a metrics/gating bug that made this invisible and, critically, prevented the policy from ever being rewarded for it via `stopball`/`softstop`.

**Evidence:** 48/48 tests pass. Live diagnostic re-validation as shown above (3000 episodes, 1519 wide, same checkpoint before/after). Training restarted (not resumed) — `stopball`/`softstop` can now actually fire on wide-crossing episodes for the first time, which is a large enough change to the achievable reward landscape that continuing the old run would conflate results.

**Process note:** this took four sequential diagnostic scripts to isolate, including catching and correcting a bug in the diagnostic tooling itself mid-investigation (the `active = wide & ~landed` filtering bug in the settle-count check). Worth remembering for future debugging in this codebase: when a "stuck" metric doesn't move despite a fix that empirical evidence says *should* move it, question the measurement before questioning the fix.

## 2026-07-09 — the ACTUAL root cause of "genuine landing rate" being meaningless all day: `_get_reach_target_y`'s settle-count mutates on every call, and it's called 7x per real physics step

**Context:** even after the `_blue_landed_was_free` classification fix above (which was real and necessary), the user kept reporting via direct play observation that the robot still visibly skipped blue and went straight for the ball. Every diagnostic this session continued to show 90-95% "genuine" landing rates, flatly contradicting that observation. User pushed back repeatedly rather than accepting the diagnostic numbers, and asked for (1) a footreach correctness check, (2) a codebase-wide audit, (3) a fresh G1 comparison. Footreach was confirmed correct (97.6% in-contact-near-blue empirically). A live foot-velocity trace even showed a seemingly genuine ~15-step near-zero-speed dwell in one sampled episode — real evidence the *mechanism* could produce genuine stops, deepening the mystery of why the aggregate rate didn't match observation.

**The training curve was the tell, in hindsight.** `Episode_Reward/blue_ball_landed`'s logged value, converted through the standard one-shot-reward formula (`event_rate = logged_value × 150 / weight`), implied only ~8% of ALL episodes (~17% of wide episodes) ever fired the landing bonus during actual training rollouts — a 5x+ gap from the ~90% every diagnostic reported on the same checkpoints. Multiple hypotheses were tested and ruled out one at a time: RSI on/off (no difference), stochastic vs deterministic action sampling (no difference, 92.8% either way), ball difficulty matched to training's current curriculum value (no difference). The one variable that finally moved the needle: **switching from play mode's per-episode `randomize_region_on_reset` to training's actual `assign_static_regions`** (permanent per-env region assignment) dropped genuine landing to 28.4% in a fresh test — a real, large, independent factor (region-specific policy specialization behaving differently under per-episode-random vs permanent-per-env conditions), but still short of explaining a further order-of-magnitude gap down toward the training curve's implied ~17%.

**Root cause, found via a fresh independent code audit (dispatched per explicit user request for another full review) plus a fresh full-codebase G1 comparison run in parallel:** `_get_reach_target_y` (`mdp/rewards.py`) is a shared helper, called once each from **7 separate reward term functions** registered in `goalkeeper_env_cfg.py` — `stopball`, `softstop`, `footreach`, `foot_proximity`, `blue_ball_landed`, `blue_overshoot_penalty`, `blue_stick_landing` — all evaluated by mjlab's `RewardManager.compute()` against the same unchanged post-physics snapshot within a single `env.step()`. The function mutates `env._blue_settle_count` (`env._blue_settle_count = torch.where(candidate, env._blue_settle_count + 1, 0)`) with **no per-step memoization guard**. Since `candidate` depends only on data fixed for the whole tick, every one of the 7 calls that tick sees the same `candidate` value and each increments the counter — so `_BLUE_SETTLE_STEPS=3` (intended to require 3 consecutive *real* 0.02s physics steps, explicitly to rule out a single-tick graze per the 2026-07-08 settle-window fix's own stated purpose) could be satisfied within a **single real tick**, the instant 3+ of those 7 calls landed on a step where the foot happened to be in contact and within radius — even for a foot merely sweeping through mid-stride. This directly defeated the settle-window's entire reason for existing.

This also resolves the earlier live-trace mystery: that trace's apparent "genuine ~15-step dwell" was real *as a physical event*, but the *registration* of `_blue_landed=True` at step 37 likely happened far earlier than 3 true consecutive ticks of contact would have required under a correctly-implemented guard — i.e., the mechanism was still registering low-quality events as landings even when a genuinely good one happened to follow, making individual traces an unreliable way to judge the aggregate criterion's strictness.

**Fix:** added `env._blue_last_settle_step` (per-env, tracks the `episode_length_buf` value at which the settle-count was last incremented). The increment (`+1`) branch now only applies when `episode_length_buf != env._blue_last_settle_step` (first call this real tick); the reset-to-zero branch (when `candidate` is false) is left unguarded since it's naturally idempotent regardless of call count.

**Validation — same checkpoint (`model_3250.pt`), same diagnostic script, only the fix applied:**

| | Before fix | After fix |
|---|---|---|
| Genuine landing rate (wide episodes) | 90-95% (every diagnostic all day) | **1.4%** |

This is the real number. The policy has not actually learned genuine multi-step stopping — the user's play observations were correct the entire time; every prior diagnostic this session was measuring an artifact of the multi-call bug, not policy quality. The `_blue_landed_was_free` classification fix from the previous entry was still a real, necessary, independent bug fix (it was correctly gating `stopball`/`softstop` on a broken signal) — but it could never have produced a meaningful genuine-rate reading while this deeper measurement bug remained.

**Evidence:** 48/48 tests pass. Live diagnostic re-validation as shown above. Also confirmed via independent code audit (fresh subagent, no access to this investigation's conclusions, arrived at the same root cause independently by static analysis of the call graph). Training restarted (not resumed) — this changes the actual achievability of the landing event during real training too (not just diagnostics), since the same multi-call pattern applies during real rollout collection.

Our port's ratchet was a real, undocumented-as-such (the "monotonic" behavior was commented as intentional but never justified against G1's actual behavior, and no prior audit pass today had checked this specific mechanism) divergence from the proven baseline.

**Why this produces exactly the observed failure:** once `ball_difficulty` hit 1.0 and the robot's fall rate increased, there was no mechanism to hand back easier practice. Every subsequent episode kept facing max-difficulty balls the current policy couldn't yet reliably handle, with less time per episode (shorter episodes) to practice anything, including the blue-ball landing task this whole investigation has been about. A transient bad patch became a permanent plateau by construction, independent of whether the settle-count fix or any reward-shaping term was otherwise working correctly.

**External validation (dispatched research pass, general-purpose subagent, WebSearch):** confirmed a pure one-way ratchet is not a recognized pattern in curriculum-RL literature. OpenAI's ADR (Rubik's Cube paper, arXiv 1910.07113 §5.2) explicitly contracts a randomization boundary when performance drops below a threshold (`p̄ ≤ t_L → φ -= Δ`), not just expands. IsaacLab's own terrain curriculum (`isaaclab_tasks/.../locomotion/velocity/mdp/curriculums.py`, `terrain_levels_vel`) explicitly promotes OR demotes each robot's terrain difficulty every episode based on distance traveled vs. commanded velocity, with no ratchet. Recommendation: match G1 exactly (fresh recompute, no floor) rather than a more complex per-env bidirectional scheme, since our difficulty is a single global scalar, not per-env terrain bins.

**Fix:** removed both `max()` calls. `env._curriculumupdate = cu` and `env._ball_difficulty = new_difficulty`, both fresh reassignments every `update_interval`, exactly matching G1's mechanism. Also fixed `ball_difficulty_curriculum`'s docstring, which described an accumulating `difficulty += step_size × curriculumupdate` formula that didn't match the actual (and unchanged) `min(1.0, curriculumupdate / 3.0)` implementation — a pre-existing doc/code mismatch, not a behavior change.

**Evidence:** 48/48 tests pass. Root cause confirmed via direct tensorboard trend inspection (`ball_difficulty` step function exactly co-occurring with the `shank_height` spike) and direct code comparison against G1's `legged_robot.py:329-336`. Fix validated only mechanically (matches G1's formula exactly) — not yet validated on a live run, since this requires a fresh training run to observe whether the plateau actually resolves.

**Not yet resolved:** whether this fix alone resolves the plateau, or whether the underlying policy capability gap at full difficulty needs separate attention (e.g. the difficulty curriculum ramping too fast relative to how hard "genuine multi-step stop-then-save" actually is to learn). The next run should be watched specifically for whether `ball_difficulty` ever dips back down after a regression, and whether episode length/shank_height recover this time instead of plateauing.

**Context:** `curriculum_ratchet_fix_2026-07-09` (previous entry) fixed the stuck-plateau symptom cleanly — live-validated `ball_difficulty` dipping 0.667→0.333 then recovering to 0.667 on its own (bidirectional curriculum working as designed), `shank_height` back to healthy baseline (~8-12 vs. the ~44 plateau), genuine landing rate measured at **43.4%** (iteration 1750) and **35.1%** (iteration 3250) — both comfortably in the "healthy" range. **This ruled out a general policy collapse** (stability metrics improving, not degrading) and is a different, more specific failure than the curriculum-ratchet bug: the robot got *better* overall while specifically abandoning the harder "genuinely stop at the intermediate waypoint" subtask.

**User granted full autonomy to research + experiment.** Dispatched two independent research passes (general-purpose subagents, WebSearch):

1. **Mechanism research** converged on a **self-reinforcing "zero collapse" + rare-event credit-assignment failure**, not classic reward hacking or entropy collapse. `blue_stick_landing`'s reward (`exp(-15*dist)*exp(-3*speed)`) is a sharp exponential cliff — once stochastic exploration pushes the policy just past this narrow basin, gradient there vanishes (arXiv:2605.30896, "zero collapse" in discontinuous-reward landscapes; actor-critic methods flagged as particularly susceptible since a biased value estimate accelerates drift once the critic starts scoring "near blue" states as low-value). Separately, rare-event scarcity (arXiv:2103.06846) means gradient-based policy search specifically degrades as a reward-bearing event's frequency falls — directly matching the 43%→35%→2% self-feeding trend. The flat `Policy/mean_noise_std` does NOT rule this out: it's a marginal per-step statistic that says nothing about whether the policy's *trajectory-level mean* still visits the narrow conjunctive joint-space basin (position + velocity + duration all satisfied together) — a policy can keep per-step noise constant everywhere while its mean approach trajectory drifts outside the capture basin entirely (a coverage-collapse, not a determinism-collapse). Mechanistically: the -30 overshoot penalty (capped at -0.5/step) is cheap, immediate, low-variance, and present in nearly every wide rollout, so it dominates the policy-gradient batch by sheer sample count even though the foregone landing bonus has higher expected value when it does land — essentially class imbalance in the PPO batch for a threshold-gated conjunctive reward.

2. **Fix research** (ALLSTEPS arXiv:2005.04323 read directly; also arXiv:2603.05113, 2104.06411, 2204.02372, 1707.05300) found ALLSTEPS itself curricula over *task difficulty distribution*, not reward-term gating — not directly applicable here. The closer match ("Decoupling Task and Behavior," arXiv:2603.05113) confirms disabling/delaying downstream reward until an upstream subtask is mastered is a real, working pattern, but both dispatched passes independently ranked the SAME lower-effort fix first: extend the existing bidirectional curriculum (already fixed in the previous entry) to also scale the stage-1 rewards (`blue_overshoot_penalty`, `blue_stick_landing`), which currently have fixed weights while `stopball`/`softstop`/`footreach`/`blue_ball_landed` all grow via the same curriculum -- letting the "must land first" incentive shrink relative to the growing gated payoff as training matures. A heavier subtask-curriculum restructure (delaying stage-2 reward, or an RSI-style episode-start curriculum spawning near blue early per JSRL/reverse-curriculum-generation) was ranked as a follow-up if this doesn't resolve it, not a first move.

**Fix applied (`curriculum_landing_gradient_fix_2026-07-09`):**
1. Added `blue_overshoot_penalty_curriculum` and `blue_stick_landing_curriculum` (`goalkeeper_env_cfg.py`), tying both to the same `reward_curriculum_ep_len` mechanism as `stopball`/`softstop`/`footreach`/`blue_ball_landed`. `blue_overshoot_penalty`: -30→-45→-60→-75 across cu=0..3. `blue_stick_landing`: 8→12→16→20.

Not yet validated on a live run — this is the first of a planned series of experiments, each to be run to 5k iterations and judged on the genuine-landing-rate trend (not just whether it avoids the specific 43%→2% collapse shape) before deciding whether to keep iterating on this direction or move to the RSI-episode-start-curriculum fallback.

**Not yet resolved:** whether this combination (curriculum-scaled penalty/bonus + widened basin) is sufficient, or whether the rare-event-scarcity mechanism specifically requires attacking exposure/practice frequency directly (the RSI-style episode-start curriculum idea) rather than just incentive magnitude and gradient shape. ## 2026-07-10 — Curriculum oscillation fix, ported from `blue-ball-waypoint`

**Context:** this branch shares `mdp/events.py`'s `reward_curriculum_ep_len`/`ball_difficulty_curriculum` classes with `blue-ball-waypoint` (the blue-ball removal only touched `rewards.py`/`goalkeeper_env_cfg.py`/`metrics.py`, not these curriculum classes). The same oscillation bug found and fixed on that branch applies here identically -- `green_ball_baseline_2026-07-10` was stopped and this fix cherry-picked over before relaunching, rather than letting a known-bad curriculum mechanism keep running on this branch too.

**Root cause (full detail in the `blue-ball-waypoint` branch history, commits `70421f8` and `cb2cb18`):** G1 uses two structurally different curriculum patterns -- reward weights are freshly overwritten every step (genuinely bidirectional), while task difficulty (`command_ranges`) is an accumulator nudged relative to its current value every ~500-step window, which is structurally incapable of decreasing since the driving signal (`curriculumupdate`) is never negative. The 2026-07-09 fix on this project correctly ported the reward-weight pattern into `reward_curriculum_ep_len`, but wrongly applied that same fresh/bidirectional pattern to `ball_difficulty_curriculum` too -- a live run on `blue-ball-waypoint` showed this causing `ball_difficulty` to oscillate 0.667<->0.333 repeatedly, never settling, with episode length bouncing noisily as a direct consequence.

**Fix:** (1) `_update_smoothed_ep_len` -- EMA (alpha=0.3) applied to `mean_episode_length` before either curriculum term computes `cu`, so single noisy windows can't flip it. (2) `ball_difficulty_curriculum` reverted to a step-size accumulator matching G1's `command_ranges` exactly (`env._ball_difficulty = min(1.0, current + step_size*cu)`), monotonic-non-decreasing by construction rather than a fresh bidirectional recompute. Independently verified against G1's actual source by 3 separately-framed subagents before being applied on the originating branch.

**External validation:** OpenAI's ADR (arXiv 1910.07113) avoids exactly this failure mode the correct way -- difficulty boundaries move by small bounded steps based on a rolling performance buffer, never an instant snap to the latest single reading.

**Independent verification:** the accumulator-vs-fresh-recompute distinction above was independently confirmed by 3 separately-framed Explore subagents (no shared context) tracing every use of `curriculumupdate` in G1's `legged_robot.py` from scratch, on the originating `blue-ball-waypoint` branch, before this fix was cherry-picked here. All three converged on the identical finding with cited line numbers.

**Evidence:** 48/48 tests pass. Standalone simulation (same as on `blue-ball-waypoint`) confirms monotonic-non-decreasing behavior under the exact noisy sequence that broke the previous version, including a simulated late-run regression. Not yet validated on a live run on this branch specifically -- `green_ball_baseline_2026-07-10` is being relaunched fresh with this fix in place per user request.

## 2026-07-10 — Left/right foot-orientation sign bug: `.abs()` let the policy skip learning the mirror-image direction for one side

**Context:** user reported "weird behavior on the arm and the orientation of the foot" specifically on the +Y (left) side while watching play, and asked for a full audit, green-ball-baseline first.

**Root cause:** `inner_face_orientation_save` and `foot_inner_face_continuous` (`mdp/rewards.py`) both rewarded the assigned foot's long axis being aligned with world/robot-local Y using `.abs()` on the dot product -- explicitly justified in the old comment as "either +Y or -Y direction is a valid sideways save." That reasoning is wrong: a left-side save needs the foot rotated toward +Y, a right-side save needs -Y -- mirror images, not interchangeable. `.abs()` rewarded either direction equally, so the policy had zero pressure to learn the correct, side-matched rotation -- it could satisfy the reward on every save by consistently rotating one way, even when that's backwards for half the cases.

**Empirical confirmation before fixing anything:** a zero-action rollout (pure physics/default pose, no learned behavior, 512 envs) showed NO left/right asymmetry in arm joint positions or foot orientation -- ruling out a robot-model/XML/default-pose bug. A rollout with the actual trained checkpoint (`green_ball_curriculum_fix_2026-07-10`, `model_7000.pt`) then showed a clear, real asymmetry: the assigned foot's quaternion z-component averaged -0.317 on right-ball envs (a genuine ~38 degree rotation toward -Y, correctly learned) vs only -0.024 on left-ball envs (~3 degrees, essentially never rotated) -- the policy learned the correct right-side rotation but never discovered the mirror-image left-side rotation, exactly matching the user's report.

**Fix:** both functions now require the SIGNED alignment to match an `expected_sign` (+1 when the left foot is closest/assigned, -1 for the right foot), derived from the empirically-confirmed-correct right-foot behavior mirrored to the left, rather than accepting either sign via `.abs()`. `foot_inner_face_continuous` (the dense, per-step version -- far more total training signal than the one-shot bonus, so the more impactful fix of the two) is left deliberately unclamped so a wrong-direction rotation gets a mild penalty, not just zero reward -- clearer gradient toward the correct mirror-image direction than merely withholding reward, which would look identical to "never rotated at all."

**Re-audit (user explicitly asked for a second, more skeptical pass rather than accepting the first fix at face value):** checked every other `.abs()` in `rewards.py` (all genuinely symmetric-by-design: distance-from-target, velocity/torque magnitude, timing windows -- none are the same bug class), re-verified `_get_correct_foot_idx`'s left=0/right=1 mapping, checked `feetorientation`/`foot_ang_vel_xy`/`single_foot_save` (all correctly symmetric by design), read the T1 XML directly (`Shoulder_Roll`/`Elbow_Yaw` correctly sign-mirrored between sides, `Shoulder_Pitch`/`Elbow_Pitch`/`Ankle_Pitch` correctly same-sign, foot body Y-offsets correctly mirrored), and compared `LeftDoubleStep`/`RightDoubleStep` AMP reference clip arm-joint ranges directly (reasonable and bounded on both sides -- these are independent real motion captures, not a synthetic mirror pair, so exact symmetry isn't expected or required). Found nothing beyond the two already-fixed functions.

**Separately investigated (same conversation, not a bug):** user asked whether G1 includes arms in its AMP observation the same way this project does, hypothesizing that AMP-driven arm motion with no grounding task reward could explain "extreme" arm movement. Confirmed: G1's `get_amp_observations()` (`legged_robot.py:157-162`) returns `self.dof_pos.clone()` -- all joints, arms included, same as this project's `joint_pos_abs`/`joint_vel_abs` (`SceneEntityCfg("robot")` default, unfiltered). No divergence in AMP observation composition. The real difference: G1 has `_reward_eereach`, a genuine ongoing task reward pulling the hand toward the ball throughout the approach, directly constraining arm motion -- this project's feet-only design has no equivalent (`postupperdofpos` only activates post-save, pulling toward a static default, not toward anything during the approach). Not fixed here -- flagged as a real architectural difference worth a deliberate design decision, not an unintentional bug, and out of this fix's scope.

**Evidence:** 48/48 tests pass. Standalone unit test verifying the sign logic against all four left/right x correct/wrong-direction combinations. Live smoke test: fresh env, reset, 60 steps, no errors.

**Not yet resolved:** not yet validated on a live training run -- both trainings are being restarted fresh with this fix per user request.
